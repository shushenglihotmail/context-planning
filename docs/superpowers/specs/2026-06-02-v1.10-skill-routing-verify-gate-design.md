## 1. Goals

Eliminate two real framework bugs surfaced by a downstream retro:

1. **Silent skill-routing failures.** `lib/provider.js#resolveSkill` checks whether the workflow provider is installed, but not whether a specific `SKILL.md` is present in the provider's catalog. Configured routings to non-existent skill names emit `invoke skill: <name>` directives that fail at runtime → per-wave `(inline-fallback)` attestation noise.
2. **Prose-only verification gates.** The `milestone.yaml` review phase routes to a code-review skill that *reads* the diff but never *runs* the code. A runtime `TypeError` shipped to `main` with full attestation because no objective execution gate existed at the wave boundary.

Both bugs combine to produce: configured routings silently fall back, fallbacks attest prose-only, and shipped code is never executed inside the milestone DAG.

## 2. Non-Goals

- Auto-installing missing skills.
- Auto-rewriting user config to repair drift.
- Fuzzy-matching skills without an explicit opt-in marker.
- Replacing the existing manual-provider safety net.
- Prompting the user mid-workflow (all runtime fallback is autonomous).

## 3. Verified Non-Bugs (no work required)

The downstream retro listed seven items. Three were verified as not framework bugs:

- **STATE.md auto-rollover** — already fixed in v1.9.0 (Bug C, commit `92d14a9`, phase `107-bug-c-complete-milestone-banner`). Downstream user was on pre-v1.9 cp. Verified by `verify-state-rollover.js` in the session.
- **Empty finalize prompt** — by design. `finalize` is `kind: scaffold` which invokes `cp milestone-finalize`. No prompt needed.
- **Auto-staging `.planning/`** — per-project policy decision, not a framework responsibility.

## 4. Design

### 4.1 Item 1 — Per-skill availability check + parens-sigil fuzzy matching

**Detection.** At workflow start, after template expansion, walk the expanded phase DAG and collect distinct `(role, skill_name)` pairs. Cost is `O(unique-skills)` (~3–5 `stat` calls for typical workflows). Fan-out and template includes do not amplify, because child phases inherit the parent template's `skill:` literal.

**Sigil syntax.** Opt-in fuzzy-match marker is parens-wrap: `(skill-name)`.

- Chosen because parens are 100% YAML-safe at any position — no quoting friction, mixable with exact-match values in the same workflow.
- Rejected: `[skill-name]` (triggers flow sequence, requires quoting), `[[skill-name]]` (doubling does not escape), `~skill~` (bare `~` is YAML null), `*skill*` (evokes glob semantics).
- Also-acceptable alternatives recorded for review: `<skill-name>`, `skill-name?`.

The sigil is a **pure flag** meaning "fuzzy is allowed for this slot." The actual match is role-driven, not pattern-driven — the sigil does *not* mean glob.

**Whole-property alternative rejected.** A parallel `X_skill_fuzzy: true` property does not scale to multi-skill phases and forces a sibling property per skill slot. In-place sigil scales naturally.

**Match algorithm (when sigil is present):**

1. Role-filter the provider catalog using `SKILL.md role:` frontmatter, so `(review)` in a reviewer role does not pick up a roadmap-reviewer in a planner role.
2. Tokenize hint and each candidate on `-` and `_` (e.g., `code-review → [code, review]`, `code-reviewer → [code, reviewer]`).
3. Score each candidate by token-overlap fraction with substring matching (so `review` ⊂ `reviewer` counts).
4. Loose threshold: `score ≥ 0.5` by default.
5. Tiebreak: highest score → shortest name → alphabetical.

**Per-skill resolution chain** (applied in order, first hit wins):

1. **Sigil-fuzzy** — if `skill_name` is wrapped in parens, run the algorithm above. Emit INFO line: chosen candidate, full candidate set, remediation hint.
2. **Exact match** — `skill_name` resolves to a real `SKILL.md` in the role-filtered catalog. Use silently.
3. **Manual provider `prompts[role]` inline** — the "manual" provider ships role-keyed prompts. Bake the prompt into the wave instruction; the agent does the work autonomously using the baked-in role prompt. No user interaction.
4. **Subagent-dispatch directive** — emit a harness-agnostic instruction: "dispatch a subagent with `role: <role>`, prompt: `<phase.prompt>`." Harness routes to its own agent system.
5. **Bare phase prompt** — last-resort fallback. Phase prompt only, no role directive.

**Diagnostic.** ONE consolidated block at workflow start, grouped by status (✓ resolved / ℹ fuzzy-matched-to-X with candidate list / ⚠ fell-back-to-manual with `cp config set` remediation hint). No per-wave attestation noise.

**Invariants.** cp NEVER auto-installs skills, NEVER auto-rewrites config, and NEVER fuzzy-matches without explicit sigil opt-in. Whole runtime fallback is autonomous (no user prompts mid-workflow).

### 4.2 Item 2 — Runtime verification gate

The review phase needs two independent layers:

- **Layer A — review quality.** Subsumed by Item 1's resolution chain. When `review_skill: (code-review)` is missing in the SP catalog, the chain falls through to the manual provider's review prompt + subagent-dispatch directive.
- **Layer B — executable verification.** Needs new pieces, because reading code is not running code.

**New pieces for Layer B:**

1. New `cp run-verify <slug>` subcommand in `bin/commands/run-verify.js` + supporting `lib/verify.js`.
2. Reads `behavior.test_command` from `.planning/config.json`.
3. Default auto-detect chain: `npm test` → `pytest` → `cargo test` → `go test ./...` → noop with WARN if none detected.
4. Exits non-zero on test failure.
5. New `verify` scaffold phase in `templates/workflows/milestone.yaml`, inserted **before** `review`, `kind: scaffold`, `command: "cp run-verify {{milestone_slug}}"`.
6. `review` phase grows `depends_on: [verify]` so review cannot run until tests pass.
7. Opt-out via `behavior.verify: false` in config OR `--skip-verify` CLI flag, for prose-only / docs-only milestones.
8. Per-project `test_command` override always wins over auto-detection.

`kind: scaffold` = real CLI execution, no LLM in the loop, **cannot be fake-attested past.**

### 4.3 Milestone authoring policy (docs)

When authoring built-in or custom workflows that route to skills:

- If the default SP catalog ships an exact-match skill → **strict** (deterministic, canonical skill always invoked).
- If no exact-match skill exists → wrap in parens for **fuzzy**, but verify the role-filtered candidate set has at least one reasonable hit.
- If nothing reasonable exists at all → leave **strict** so the runtime falls all the way through to subagent-dispatch with the role prompt.

**Fuzzy is the exception, not the rule.** Concrete `milestone.yaml` example:

```yaml
brainstorm_skill: brainstorming      # strict — SP ships it
plan_skill: writing-plans            # strict — SP ships it
review_skill: (code-review)          # fuzzy — SP has no match
```

## 5. Components & Boundaries

| Component | Owns | Depends on |
|---|---|---|
| `lib/provider.js` | Parens-sigil parser, role-filtered token-overlap fuzzy matcher, per-skill `SKILL.md` stat, manual-provider prompt loader | filesystem, provider config |
| `lib/runtime.js` | Workflow-start diagnostic aggregator, per-skill resolution chain wiring, subagent-dispatch directive emission | `lib/provider.js`, phase DAG |
| `lib/verify.js` | Test-command auto-detect, exec wrapper, exit-code propagation | child_process, `.planning/config.json` |
| `bin/commands/run-verify.js` | CLI entrypoint for `cp run-verify` | `lib/verify.js` |
| `templates/workflows/milestone.yaml` | DAG shape: insert `verify` before `review`, wire `depends_on` | (data only) |

Each unit is independently testable. `lib/verify.js` has no awareness of provider/skill machinery; `lib/provider.js` changes do not touch DAG execution; `lib/runtime.js` changes touch only the resolution layer and the start-of-workflow diagnostic.

## 6. Data Flow

```
cp run milestone <name>
  └─ runtime expands template → phase DAG
       └─ diagnostic pass: walk DAG, collect (role, skill_name) pairs
            └─ for each pair: resolution chain (sigil-fuzzy → exact → manual → dispatch → bare)
                 └─ emit ONE diagnostic block (✓/ℹ/⚠)
       └─ execute wave-by-wave; each phase carries its resolved skill/prompt
            └─ verify wave: invoke `cp run-verify <slug>` → lib/verify.js → exit code
                 └─ on failure: wave fails, review wave blocked by depends_on
```

## 7. Error Handling

- **Skill not found at runtime** (post-diagnostic): cannot happen — diagnostic pass surfaces all misses at workflow start.
- **Fuzzy match: no candidates** above threshold → fall through to manual provider; diagnostic emits `⚠ fell-back-to-manual` with remediation hint.
- **`cp run-verify` no test command detected** → emit WARN and exit 0 (do not fail the wave; user can `behavior.test_command` to set explicit).
- **`cp run-verify` test command failure** → exit non-zero, scaffold phase fails, review phase blocked, user sees real CLI output.

## 8. Testing

- **`lib/provider.js`** — unit tests for parens-sigil parser (boundary cases, malformed); fuzzy matcher (token overlap, role filter, tiebreak determinism); skill-existence stat (present/absent/symlink).
- **`lib/runtime.js`** — integration tests for resolution chain (each layer hits expected fallback); workflow-start diagnostic format snapshot.
- **`lib/verify.js`** — unit tests for auto-detect chain priority; exec exit-code propagation; opt-out behavior.
- **`templates/workflows/milestone.yaml`** — integration test: full milestone run on a synthetic fixture; verify phase blocks review on failure; `--skip-verify` works.

- Refactoring the manual provider's prompt catalog (orthogonal).
- Cross-provider fuzzy matching (single-provider scope sufficient for v1.10).
